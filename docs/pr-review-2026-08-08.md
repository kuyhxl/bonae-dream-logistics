### 2. Flyway V3 버전 충돌 (delivery-route-schema ↔ delivery-route-units)

두 브랜치가 **같은 버전 번호**로 서로 다른 마이그레이션을 추가합니다.

- `V3__align_delivery_route_with_hub_contract.sql` (DROP → ADD 방식, 기존 데이터 소실)
- `V3__alter_delivery_route_units.sql` (RENAME + 값 변환 방식, 데이터 보존)

둘 다 머지되면 Flyway가 `Found more than one migration with version 3`로 기동 실패합니다.
추가로 **양쪽 모두 `uk_p_deliveries_active_order` 인덱스를 생성**해서 뒤에 도는 쪽이 반드시 실패합니다.

→ 한 브랜치로 합치거나, 하나를 V4로 올리고 중복 DDL을 제거해야 합니다.
데이터 보존 관점에서는 units 쪽(RENAME + 변환)이 맞는 방향입니다.

### 3. `created_by varchar(10)` vs X-User-Id(UUID 36자)

`common/.../AuditorAwareImpl`은 `X-User-Id` 헤더 값을 그대로 감사 컬럼에 넣는데,
모든 마이그레이션의 `created_by / updated_by / deleted_by`가 `varchar(10)`입니다.
`User.id`는 UUID(36자)라서 **게이트웨이가 헤더를 채우기 시작하는 순간 모든 INSERT가 터집니다.**

지금 통과하는 이유는 헤더가 없어서 `"SYSTEM"`(6자)으로 폴백되기 때문일 뿐입니다.
`BaseEntity`의 `length = 10`과 DDL을 함께 `varchar(36)` 이상으로 올리거나,
`X-User-Id` 대신 `username`(varchar(10))을 감사 주체로 쓰도록 정하고 게이트웨이 계약에 명시해야 합니다.

허브 생성/수정 API(feature/76)가 이 경로를 처음 타는 코드라 여기서 먼저 터질 겁니다.

## 🟡 Minor / 개선 제안

### hub-service (feature/76-hub-crud)

전반적으로 완성도 높습니다. 1차 중복검사 + DB 부분 유니크 인덱스 이중 방어, 제약조건명으로 에러 구분, 삭제 시 연관 HubRoute 비활성화까지 잘 짜여 있습니다.

- **LIKE 와일드카드 미이스케이프**: `LIKE CONCAT('%', :keyword, '%')`에서 `%`, `_`가 그대로 패턴으로 동작합니다. 키워드 `%` 하나면 전건 조회. 이스케이프 처리 또는 `ESCAPE` 절 추가 필요.
- **대소문자 구분 검색**: 영문 허브명이 생기면 `LOWER()` 또는 `ILIKE` 필요. 앞뒤 `%` LIKE라 인덱스도 못 타니 데이터가 커지면 full scan입니다.
- **`HubUpdateRequest.isEmpty()` 허점**: `{"name": "   "}`이면 `getName()`이 `""`를 반환해 `isEmpty()`를 통과 → 불필요한 중복 조회 쿼리 후 `INVALID_HUB_NAME`. `isBlank()` 기준으로 null 처리하는 게 깔끔합니다.
- **검증 중복**: DTO Bean Validation과 엔티티 `validateXxx`가 동일 규칙을 두 번 검사합니다. 방어적 설계로 의도한 거면 OK지만, 규칙 변경 시 두 곳을 고쳐야 한다는 점 인지 필요.
- **`OperationCustomizer` (X-User-* Swagger 노출)**: 모든 오퍼레이션에 붙습니다. "임시"라고 주석에 있으니 `@Profile("local")`로 감싸거나 제거 이슈를 별도로 등록해 두세요.
- **삭제 시 연관 라우트 처리**: 전건 로딩 후 dirty checking이라 라우트가 많으면 N건 UPDATE입니다. 벌크 `@Modifying` 쿼리 고려.
- 파일 상당수 EOF 개행 누락 (`HubController`, `Hub`, `OpenApiConfig`, `HubUpdateRequest`, `HubListItemResponse`).
